## [SEVERITY: blocking] `full_retrain` is reachable from the network on a 512 MB box, with no guard

- `backend/app/ml/train_pipeline.py:180` (`full_retrain`, no guard of any kind)
- Reached via `backend/app/services/upload_service.py:96`, mounted unconditionally at
  `backend/app/main.py:99` (`app.include_router(upload.router)`)

**What is wrong.** A successful upload triggers `full_retrain` in a background task.
Training peaks around **2.3 GB** (measured in CI earlier today); the serving container has
**512 MB** and is killed, not throttled, when it exceeds that. `full_retrain` takes no
argument and consults no setting that could refuse to run in a serving context — it starts
building the training frame immediately.

The protection that exists is **frontend-only**: `VITE_ENABLE_UPLOAD=false` merely stops
the panel being built (`frontend/src/components/model/ModelPage.tsx:14`). Nothing
server-side declines the request. This is the same class as the "Refresh now" button fixed
earlier today — a control hidden in the UI while the endpoint stays open — but the
consequence is worse, because this one ends the process rather than failing.

**How it was confirmed.**
```
grep -rn "full_retrain" app/            -> upload_service.py:96 calls it
grep -n "include_router" app/main.py    -> line 99 mounts upload unconditionally
sed -n '/^def full_retrain/,/try:/p'    -> no memory, env or context check
grep -rn "VITE_ENABLE_UPLOAD" app/      -> zero hits in backend; frontend only
curl -X POST https://sanket-a0dd.onrender.com/api/upload   -> HTTP 422
curl .../openapi.json                   -> /api/upload and /api/upload/{batch_id}/
                                           confirm-mapping are publicly documented
```
**422, not 404 or 403**, is the point: the endpoint is live and validating input, so a
well-formed multipart upload is accepted rather than refused.

**Suggested fix (not applied).** Refuse at the boundary rather than hiding the control.
A `settings.allow_training` flag (default true; false in `render.yaml`) checked at the top
of `full_retrain`, returning a `TrainReport(status="refused")`, plus a 409 from the upload
route. Guarding `full_retrain` itself rather than only the route matters because it is also
reachable from `refresh_for_deploy`, where it *must* keep working.

**Related, same shape, lower impact.** `/api/ingest/run-cycle`, `/api/ingest/backfill` and
`/api/ingest/refresh-observations` are also publicly mounted and equally unguarded; the
first was hidden in the UI today but not closed server-side.

## [SEVERITY: concerning] A second route into `full_retrain`, via a daemon thread, one env var away

- `backend/app/live/orchestrator.py:277-279`

**What is wrong.** After a *final*-tier observation refresh ingests at least
`live_retrain_min_new_rows` rows, the orchestrator spawns `run_retrain` on a raw
`threading.Thread(daemon=True)`. That reaches the same unguarded `full_retrain` as
finding 1, so the same ~2.3 GB peak applies, on a 512 MB box.

It is **dormant today** only because `LIVE_INGEST_ENABLED=false` on the serving host, which
stops the scheduler from ever calling the refresh. It is not dormant by design: nothing in
this path checks whether training is permissible in this process. Setting that one env var
to `true` — the same variable someone might flip to make "Refresh now" work — arms it.

The ordering itself is correct and worth stating, since it was the thing being looked for:
the thread starts *after* the batch is written and *after* `inference.invalidate_caches()`
(line 265), so there is no read-before-write here.

**How it was confirmed.**
```
sed -n '262,300p' app/live/orchestrator.py
  -> line 265  inference.invalidate_caches()      (write completes first)
  -> line 277  from app.services.upload_service import run_retrain
  -> line 278  threading.Thread(target=run_retrain, ... daemon=True).start()
grep -rn "full_retrain" app/   -> upload_service.py:96, reached by run_retrain
```
Live confirmation that it is currently dormant:
```
curl -s .../api/ingest/status | ... -> "enabled": false,
                                       scheduler {"running": false, "ticks_completed": 0}
```

**Suggested fix (not applied).** The same guard proposed in finding 1, checked inside
`full_retrain`, closes this path too — which is the argument for guarding the function
rather than each of its callers. `daemon=True` is separately worth noting: a retrain in
flight when the platform stops the container is killed mid-write, which is safe only
because `registry.set_current()` runs last.

## [SEVERITY: cosmetic] An empty `LIVE_GEFS_MEMBERS` crashes on `members[0]` instead of saying so

- `backend/app/live/gefs.py:423` — `choose_transport(init, cycle_hour, members[0])`
- Reached from `backend/app/live/orchestrator.py:154` — `members = settings.gefs_member_list`

**What is wrong.** `gefs_member_list` filters out empty entries, so a blank or
comma-only env var yields `[]`. `fetch_cycle` then indexes `members[0]` before anything
validates the list, raising `IndexError` rather than reporting a configuration problem.
The cost is low — the orchestrator catches it, marks the `IngestRun` failed with the
exception text, and the pipeline log now shows that honestly — but the message a reader
gets is `IndexError: list index out of range`, which does not name the cause.

**How it was confirmed.**
```
python -c "from app.config import Settings; print(Settings(live_gefs_members='').gefs_member_list)"
  -> []
python -c "... Settings(live_gefs_members=' , , ').gefs_member_list"
  -> []
grep -n "gefs_member_list" app/live/orchestrator.py   -> line 154 feeds fetch_cycle
sed -n '415,432p' app/live/gefs.py                    -> line 423 indexes [0] unguarded
```
Not reachable on the deployed host today: live ingestion is disabled there, and the value
is only read when a pull actually runs.

**Suggested fix (not applied).** An early `if not members: raise ValueError("LIVE_GEFS_
MEMBERS is empty; nothing to fetch")` in `fetch_cycle`, so the failure names itself. The
five members are load-bearing — the model was trained on exactly `gec00,gep01..gep04` and
widening the set needs a retrain — so a silent empty list is worth refusing loudly.

## Checked and found sound (recorded so the next pass does not redo them)

- **Cache thread-safety** (`ml/inference.py`) — every `_score_cache` and `_state_cache`
  access is inside `with _lock:` (lines 74, 103, 111, 188, 269). The cache is bounded at
  `_SCORE_CACHE_MAX = 24` with oldest-insert eviction. No race found.
- **Train/serve feature parity** — the biggest risk from today's split of training data
  from serving data. `historical_bust_frequency` is loaded from the *model run*
  (`inference.py:98`, `registry.load_historical_bust_freq`), never recomputed from the
  serving store, so a box holding fewer cycles than the model trained on cannot silently
  shift a feature.
- **Store reads in scope are all projected** — every `read_dataset` call in `ml/` and
  `live/` passes `columns=` (`inference.py:136,204,215`; `train_pipeline.py:107,117,126`).
  No unbounded full-store read of the kind `dataset_summary()` needed guarding for.
- **SHAP shape handling** (`ml/explain.py:34-60`) — handles the list-vs-array API
  difference explicitly, guards `sv.shape == X.shape`, and returns `None` on any failure.
- **`compact_store` vs `cycle_already_ingested`** — item 4's main candidate. The DB says a
  cycle is ingested while compaction can delete partitions, but compaction only removes
  rows a surviving batch supersedes, so store and DB cannot diverge. Sound.
- **`GroupKFold` with one group** (`ml/regressors.py:103-122`) — the `n_groups < 2` early
  return fires before `GroupKFold(n_splits=splits)` is constructed.
- **Post-ingest ordering** (`live/orchestrator.py:265-279`) — the batch is written and
  caches invalidated before the retrain thread starts. No read-before-write.
- **`spans.pop()`** (`live/gefs.py:246`) — guarded by `if spans and ...`.
